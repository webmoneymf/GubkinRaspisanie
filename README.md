# Расписание Губкинского университета — филиал Оренбург

Адаптивный frontend на HTML/CSS/JavaScript. Поддерживает выбор группы, недельный и дневной просмотр, ручное и автоматическое обновление, локальный кеш последнего успешного ответа, состояния отмены/переноса и сведения о преподавателях/аудиториях.

## Подключение официального API

По двум HAR-файлам из DevTools подтверждены следующие публичные запросы:

- Список групп: `GET https://lk.gubkin.ru/schedule/api/api.php?act=list&method=getFacultyGroups&facultyId=15`
- Расписание: `GET https://lk.gubkin.ru/schedule/api/api.php?act=schedule&date=17-11-2026&groupId=10568`

В `config.js` эти адреса уже настроены. Дата в запросе расписания автоматически формируется как текущая дата в формате `ДД-ММ-ГГГГ`, а ID группы подставляется из выбранной группы.

В HAR подтверждены параметры `facultyId=15`, пример `groupId=10568` (группа `ОРГ-26-02`) и филиал Оренбург с `organizationId=1`. Ответ расписания содержит `week`, `organizations`, `lessonsTimeChunks` и `lessons`. Время занятия вычисляется по индексам `timeChunks` из расписания Оренбурга. Учитываются преподаватели, аудитории, тип занятия, отмены и переносы.

Внимание: HAR подтверждает успешный ответ сервера в браузере на официальном сайте, но сам по себе не доказывает, что API разрешает запросы с другого домена. Перед публикацией проверьте приложение на локальном сервере и вкладке Console/Network. См. раздел CORS ниже.

## Запуск локально

Из папки проекта выполните `python -m http.server 8080`, затем откройте http://localhost:8080.

## CORS и публикация

GitHub Pages — статический хостинг. Браузер сможет напрямую читать API только если сервер университета разрешает CORS для origin опубликованного сайта. Если браузер сообщает `CORS policy` или `Failed to fetch`:

- корректное решение — небольшой серверный proxy (например, Cloudflare Worker / собственный backend), который обращается к API на серверной стороне;
- proxy должен разрешать только конкретные пути API и методы, а не быть открытым прокси;
- секреты, если они действительно требуются, хранить только в переменных окружения backend;
- если API ограничен российскими IP/сетевым периметром, proxy должен размещаться в разрешённой серверной сети. Не пытайтесь обходить авторизацию или сетевые ограничения с клиентского кода.

После появления proxy URL можно прописать в `config.js` как endpoint-ы. Для GitHub Pages сам сайт остаётся статическим.

## Публикация на GitHub Pages

1. Создайте GitHub-репозиторий, например `gubkin-schedule`.
2. Загрузите `index.html`, `styles.css`, `app.js`, `config.js`.
3. Откройте Settings → Pages.
4. В разделе Build and deployment выберите `Deploy from a branch`, ветку `main`, папку `/ (root)`.
5. Сохраните. После публикации откройте выданный GitHub Pages URL.

## Автообновление и кеш

- Интервал по умолчанию — 120 секунд (`refreshIntervalMs`), минимум 60 секунд.
- Повторный запрос не стартует, пока предыдущий не завершился.
- Последний успешный ответ хранится в `localStorage`.
- При сетевой ошибке отображается последнее сохранённое расписание и время его получения.
- Ручное обновление доступно кнопкой «Обновить».
